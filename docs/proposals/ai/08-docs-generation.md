# Documentation & Onboarding Generation from `.emod`

> Part of the [emod AI proposals](./README.md). Assumes the shared [LLM foundation](./00-llm-foundation.md) (the `llm.Model` port and Bedrock-backed Claude) and does not re-specify it.

## Problem

An `.emod` file is a precise, machine-checkable description of an event-driven
system — but it is not how a new engineer wants to *learn* one. Faced with
`examples/inbound_customer_comms_agentic_reply.emod`, a newcomer sees five
contexts, sixteen-odd slices, and a web of automations crossing context
boundaries (`target context OutboundDelivery`, `target context CollectionHolds`,
`target context ConversationHoldScheduling`). What they actually need is a
sentence: *"an inbound email arrives, we identify the customer, classify the
message, and either auto-reply or open a case — and while a conversation is live
we pause dunning."* That narrative is latent in the model, but reconstructing it
by hand from the DSL is exactly the onboarding tax we want to remove.

The usual answer is a hand-written `README` or a Confluence page. It is correct
the day it is written and wrong a month later, because the model is the source of
truth and the prose is a copy. Diagrams pasted into docs rot the same way. Every
team that has tried to keep an architecture doc in sync with the code knows this.

emod is unusually well-positioned to do better, for two reasons. First, the model
is already *structured and exportable* — `emod export -f json` gives a complete,
named, position-tagged tree, and `emod diagram -f mermaid` renders the same model
as an embeddable diagram. Second, the example models already carry **authorial
intent inline**: every slice in `examples/inbound_customer_comms_agentic_reply.emod`
has a `#` comment stating what it is for ("Resolve the inbound message to a known
customer, or defer for ID-ask.", "While an AI conversation is active, block
outbound dunning by applying a hold."). Those comments are captured in the export
as `comments` arrays on every node. So docs generation here is not "hallucinate a
description of unknown code" — it is "expand intent the author already wrote,
grounded on a structured model we can cross-check names against." That is a much
safer LLM task, and it is the one this proposal specifies.

## Goals

- A CLI command that turns an `.emod` file into human-readable Markdown
  documentation: `emod ai docs file.emod -o docs/`.
- Three output styles for three audiences:
  - `--style reference` — per-context reference pages: every aggregate, slice,
    command, event (with fields), view, automation, translation, catalogued.
  - `--style narrative` — a prose walkthrough per context → aggregate → slice →
    flow, reading as connected paragraphs rather than a catalogue.
  - `--style onboarding` — a single guided tour: "here's how an inbound email
    becomes a reply, step by step," following the actual automation chain across
    contexts plus an executive summary of the whole system.
- Embedded diagrams generated by emod itself (`--with-diagrams`), not by the
  model: the prose explains a `mermaid eventmodeling` block that emod produced,
  so the picture is always faithful to the source.
- **Faithfulness by construction**: every flow, command, event, view, and
  automation the prose names must exist in the model. The generator grounds on
  `emod export -f json` and cross-checks the model's output against those names.
- Honour the per-slice `#` comments as authorial intent — expand and connect
  them, never contradict them.
- Cheap by default: Haiku for the mechanical per-section passes, Opus only for the
  synthesized executive summary and onboarding walkthrough.
- A drift story: docs are *derived*, so regenerating them in CI keeps them in sync
  with the model — `emod ai docs --check` fails the build when committed docs no
  longer match what the model would produce.
- Zero impact on existing commands; opt-in and absent without configured
  credentials, per the foundation's configuration section.

## Non-Goals

- Question answering over a model — that is [proposal 07](./07-talk-to-your-model-qa.md).
  This produces static docs, not an interactive session.
- Generating BDD scenarios or sample payloads from flows — that is
  [proposal 09](./09-bdd-test-generation.md).
- Editing or generating the model itself — generation is
  [01](./01-nl-to-model-generation.md), editing is
  [10](./10-conversational-viewer-editing.md). Docs generation is strictly
  read-only over an existing, valid model.
- Inventing a new diagram renderer. Diagrams come from the existing
  `internal/diagram` (`-f mermaid`); the model only writes prose *around* them.
- Re-specifying the `llm.Model` port, the Bedrock adapter, or model selection —
  all defined in the foundation.

## How It Works

### Where it plugs into the pipeline

Docs generation is a pure consumer of the existing pipeline. It never produces
`.emod` and never needs the repair loop — there is nothing to validate back into
emod. The flow is:

```
file.emod ──▶ parser → validator → linter   (must be clean: refuse to document a broken model)
     │
     ├──▶ emod export -f json   (the grounding fact base: every name, field, comment)
     │
     └──▶ emod diagram -f mermaid (per context)   (the embeddable diagrams)
                              │
                              ▼
                 internal/ai/docs: assemble per-section prompts
                              │
                              ▼
            llm.Model.Generate  (Haiku per section, Opus for the synthesis)
                              │
                              ▼
            faithfulness check: every named entity ∈ export name set
                              │
                              ▼
              Markdown tree (or single file) under -o
```

The model-facing logic lives in a new `internal/ai/docs` package, depending only
on `llm.Model` plus the existing `internal/export`, `internal/diagram`,
`internal/parser`, `internal/validator`, and `internal/linter`. The CLI command is
a thin wrapper in `internal/cli`, matching the existing `RunExport` / `RunDiagram`
/ `RunSlices` actions in `internal/cli/app.go`.

The generator **refuses to document an invalid model**: it runs the validator
first and exits non-zero on errors, because documenting a broken model would
produce confident prose about flows that do not parse. (Lint warnings are
non-fatal but surfaced — you can document an un-idiomatic model, you just get told.)

### Grounding: export JSON + slice comments

The fact base is `ExportJSON` (`internal/export/export.go`). It is the right
grounding source because it is the *whole* model, structurally, with the
properties this feature needs:

- Stable names at every level — `model.name`, `contexts[].name`,
  `aggregates[].name`, `slices[].name`, `commands[].name`, `events[].name` (with
  `fields[]`), `views[].name` (with `subscribes[]`), `automations[]`
  (`trigger_event`, `command`, `target_context`), `translations[]`
  (`external_system`, `reads`, `command`, `event`), and `flows[]`
  (`command_name` → `event_name`).
- The `comments` array on **every** node, carrying the inline `#` text. For the
  example model, `slices[].comments[0].text` is precisely the per-slice intent the
  author wrote. This is the single most valuable grounding signal: it is a human's
  one-line summary of each unit of behaviour, and the model's job is to expand and
  connect those summaries, not to guess them.

The prompt for each section carries the relevant export sub-tree (the context, or
a single slice) plus an explicit instruction: *the `comments[].text` is the
author's stated intent; honour it, expand it, never contradict it; if a comment
and the structure disagree, say so rather than invent a reconciliation.*

The generator also reuses `emod slices` (`internal/cli/slices.go`) for the
per-slice **pattern label** — `command`, `view`, `automation`, `translation` —
which `detectPattern` already computes. Telling the model "this slice is an
*automation* pattern: trigger event → command → target context" anchors the prose
in emod's own vocabulary rather than letting the model improvise structure names.

### Document structure

One context is one section (reference) or one chapter (narrative/onboarding). The
default `-o docs/` writes a tree; `--single-file` collapses it to one Markdown
file (useful for a PR description or a single embedded page).

```
docs/
  README.md                      # exec summary + system map + index of context pages
  contexts/
    inbound-email.md             # context "InboundEmail"
    outbound-delivery.md         # context "OutboundDelivery"
    customer-cases.md            # context "CustomerCases"
    collection-holds.md          # context "CollectionHolds"
    conversation-hold-scheduling.md
  onboarding.md                  # only with --style onboarding: the cross-context walkthrough
```

Each context page has a fixed skeleton the generator fills:

1. **Purpose** — one paragraph synthesized from the context name, its aggregate,
   and the slice comments.
2. **Diagram** — an embedded `mermaid eventmodeling` block for that context,
   produced by `emod diagram -f mermaid` (see below), followed by a paragraph the
   model writes *explaining* the diagram.
3. **Walkthrough / Reference** — per slice, in source order: what triggers it,
   the command it issues, the event(s) it records, where automations route next.
4. **Inbound / outbound edges** — which events this context emits that other
   contexts react to, and which commands arrive from elsewhere. This is computed
   deterministically from the automations' `target_context` and the views'
   `subscribes`, then narrated — it is the part humans most need and least get
   from reading slices in isolation.

The `README.md` exec summary and the `onboarding.md` walkthrough are the only
sections that reason across the *whole* model at once, so they are the only ones
routed to Opus.

### Embedding emod's diagrams

The model does not draw. For each context the generator shells out to (or calls
in-process) the existing diagram path:

```
emod diagram file.emod -f mermaid
```

which emits Mermaid's `eventmodeling` block (the `tf NN <type> <ns>.<id>` form
produced by `internal/diagram/mermaid.go`, grouped into per-context swimlanes via
namespace dot-notation). That block is embedded verbatim in a fenced
```` ```mermaid ```` code block, and the model is asked only to write the
surrounding explanation — what the swimlane shows, which timeframe is the trigger,
where the automation hands off. Because the diagram is generated by emod from the
same source, it cannot drift from the model, and the model is never in a position
to draw a flow that does not exist.

For multi-context diagrams (the onboarding walkthrough), the same command renders
the full model; the projected swim-lane and DCB query-lens styles
(`--style projected|dcb`, already in `diagram`) are available when the model uses
DCB contexts.

### Faithfulness: don't invent flows

The whole risk of doc generation is the model writing a plausible flow that is not
in the model. emod can mechanically rule that out, because it has the complete set
of legal names from the export. After each section is generated, the generator
extracts the **entity names the prose references** (it asks for them as structured
output, see below) and checks each against the name set built from the export:

```go
// names() flattens the export into the set of every nameable entity:
// contexts, aggregates, slices, commands, events, views, automations,
// translations, plus flow endpoints (command_name, event_name).
func (f *factBase) verify(claimed []claimedRef) []driftFinding {
    var out []driftFinding
    for _, c := range claimed {
        if !f.has(c.Kind, c.Name) {
            out = append(out, driftFinding{Section: c.Section, Ref: c}) // an invented name
        }
        // also assert claimed flows exist as command→event edges
        if c.Kind == "flow" && !f.hasFlow(c.Command, c.Event) {
            out = append(out, driftFinding{Section: c.Section, Ref: c})
        }
    }
    return out
}
```

If a section references a name not in the model — `EmailConversationAutoReplied`
when the real event is `EmailConversationReplyInitiated` — that section is
regenerated once with the offending names fed back ("`EmailConversationAutoReplied`
does not exist in this model; the events in slice *Compose auto-reply* are:
`EmailConversationReplyInitiated`"). On a second failure the generator emits the
section with the unverifiable claims flagged inline and exits non-zero under
`--strict`. This is a *deterministic faithfulness gate*, the documentation
analogue of the generate-side repair loop: the model does not have to be perfectly
faithful in one shot, it has to converge against names emod owns.

Structured output makes this checkable. Per the foundation, each section call
returns not just prose but the entities it referenced, via the
`GenerateRequest.Schema` path:

```json
{
  "type": "object",
  "required": ["markdown", "referenced"],
  "properties": {
    "markdown":   { "type": "string", "description": "the section body" },
    "referenced": {
      "type": "array",
      "description": "every model entity named in the markdown",
      "items": {
        "type": "object",
        "required": ["kind", "name"],
        "properties": {
          "kind": { "enum": ["context","aggregate","slice","command","event","view","automation","translation","flow"] },
          "name": { "type": "string" },
          "command": { "type": "string" },
          "event":   { "type": "string" }
        }
      }
    }
  }
}
```

The `referenced` array is what `verify` consumes. It also doubles as a coverage
check: a context page that never references half its slices is incomplete, and the
generator can warn on it.

### Cost: Haiku per section, Opus for synthesis

Most of a docs run is mechanical: "given this one slice's export sub-tree and its
`#` comment, write two paragraphs." That is a low-stakes, well-grounded,
small-context task — exactly the Haiku case from the foundation's selection table.
Each context's per-slice prose runs on `anthropic.claude-haiku-4-5` at `low`/`medium`
effort, and these calls fan out concurrently across slices.

Only two outputs require reasoning over the entire system: the executive summary
in `README.md` and the cross-context `onboarding.md` walkthrough. Those route to
`anthropic.claude-opus-4-8` at `high` effort with adaptive thinking, because
getting "here's how the whole thing fits together" right is the high-value part
and the part a cheap model gets shallowly wrong. `Response.Usage` is accumulated
across all calls and reported once at the end, consistent with the bedrock-cost
tooling.

## Interface

A `docs` subcommand under the `ai` command group introduced in
[proposal 01](./01-nl-to-model-generation.md), mirroring the existing command
structure in `internal/cli/app.go` (urfave/cli v2, `LintError` exit codes).

```
emod ai docs <file> [flags]

Flags:
  -o, --output <dir>      directory to write the docs tree (default: ./docs)
      --style <style>     reference | narrative | onboarding (default: narrative)
      --with-diagrams     embed emod-generated mermaid diagrams (default on)
      --single-file       write one Markdown file instead of a tree
      --diagram-style <s> projected | dcb | auto, passed through to `diagram` (default auto)
      --check             regenerate and diff against existing docs; exit 1 on drift (CI)
      --effort <level>    overall effort for the synthesis pass (default high)
      --strict            exit non-zero if any section fails the faithfulness check
      --show-cost         print token usage and cost summary (default on for a TTY)
```

Example invocation:

```
$ emod ai docs examples/inbound_customer_comms_agentic_reply.emod \
    --style onboarding -o docs/inbound

validating model... clean (5 contexts, 16 slices)
exporting model + rendering 5 context diagrams...
  InboundEmail .............. 11 slices  (haiku)
  OutboundDelivery .......... 2 slices   (haiku)
  CustomerCases ............. 3 slices   (haiku)
  CollectionHolds ........... 3 slices   (haiku)
  ConversationHoldScheduling. 3 slices   (haiku)
synthesizing executive summary + onboarding walkthrough... (opus, effort=high)
faithfulness check: 22/22 referenced entities resolved
wrote docs/inbound/README.md, docs/inbound/onboarding.md, 5 context pages
tokens: 38,400 in / 14,100 out  (~$0.34)
```

In CI, the drift gate:

```
$ emod ai docs examples/inbound_customer_comms_agentic_reply.emod --check -o docs/inbound
docs/inbound/contexts/inbound-email.md is out of date (model changed since last generation)
run: emod ai docs examples/inbound_customer_comms_agentic_reply.emod -o docs/inbound
exit status 1
```

`--check` regenerates with a fixed seed/recorded model where determinism matters
(see Open Questions on determinism); the practical CI contract is "the committed
docs match a fresh generation," so docs cannot silently diverge from the source.

## Worked Example

Take the **InboundEmail** context, and within it the *Compose auto-reply* slice
from `examples/inbound_customer_comms_agentic_reply.emod`. Its grounding facts,
from the export, are: the slice comment `# Standard auto-reply for an identified,
non-escalated message.`; the command `EmailConversationInitiateReply`; the event
`EmailConversationReplyInitiated`; the flow
`EmailConversationInitiateReply -> EmailConversationReplyInitiated`; and the
automation `EmailConversationComposeReply` (`trigger
EmailConversationClassified`, `command EmailConversationInitiateReply`, `target
context InboundEmail`). `emod slices` labels the slice pattern `automation`.

The generated narrative section (style `narrative`) reads roughly:

> ### Compose auto-reply
>
> Once a message has been classified and is not flagged for escalation, the
> system composes a standard automated reply. The `EmailConversationComposeReply`
> automation listens for `EmailConversationClassified` and issues the
> `EmailConversationInitiateReply` command, which records
> `EmailConversationReplyInitiated`. That event carries the context the outbound
> side needs — `customerId`, `providerMessageId`, `category`, `rfc822MessageId`,
> `inReplyTo`, and the `modelVersion`/`confidence` of the classification that
> drove the reply.
>
> `EmailConversationReplyInitiated` is a hinge in the model: three other slices
> react to it. *Send outbound reply* hands it to the **OutboundDelivery** context,
> *Apply conversation hold* pauses dunning in **CollectionHolds**, and *Schedule
> hold expiry* parks a wake-up in **ConversationHoldScheduling** so the hold
> auto-releases after a quiet window. Reading the slice alone you would miss the
> last two; they are how a live AI conversation suspends collections.

Every named entity in that paragraph — the command, the event, the automation,
the three reacting slices, the three target contexts, the listed fields — exists
in the export, and the cross-context "three slices react to it" is computed from
the automations whose `trigger_event` is `EmailConversationReplyInitiated`, not
guessed. The second paragraph is the value docs generation adds over reading the
DSL: it connects a slice to its downstream reactions, which the source spreads
across `slices` *Send outbound reply*, *Apply conversation hold*, and *Schedule
hold expiry*.

The context page embeds the emod-generated diagram for **InboundEmail**, produced
by `emod diagram examples/inbound_customer_comms_agentic_reply.emod -f mermaid`:

````markdown
```mermaid
eventmodeling

% Inbound Customer Comms Agentic Reply

% Slice: Compose auto-reply
tf 07 evt InboundEmail.EmailConversationClassified
tf 08 cmd InboundEmail.EmailConversationInitiateReply
tf 09 evt InboundEmail.EmailConversationReplyInitiated
...
```
````

followed by the model's explanation of that swimlane. The diagram is emod's
output verbatim, so it cannot contradict the model; the prose only interprets it.

For the **onboarding** style, the same slice appears inside the cross-context
walkthrough as one step in the chain *inbound received → identified → classified →
reply initiated → (delivered ∥ hold applied ∥ hold scheduled → released)*, which is
the executive-summary view a new engineer actually needs and the part that runs on
Opus.

## Implementation Plan

**Phase 1 — Fact base + reference style (M).** `internal/ai/docs`: build the
`factBase` from `ExportJSON` (name set, flow edges, per-node comments, per-slice
pattern from `detectPattern`). Implement `--style reference` with **no LLM** first
— a deterministic catalogue rendered straight from the export, including the
computed inbound/outbound context edges. This ships value immediately (faithful by
construction, zero cost) and gives the later styles a verified skeleton to expand.

**Phase 2 — Per-section LLM prose + faithfulness gate (M).** Add `--style
narrative`: per-slice Haiku calls grounded on the slice sub-tree and its `#`
comment, structured output (`markdown` + `referenced`), and the `verify` check
against the fact base with one feedback-driven regeneration. Concurrency across
slices. Unit-tested against a mock `llm.Model` (canned sections that reference
real names, invented names, and a converge-on-retry case), per the repo's Go test
conventions.

**Phase 3 — Diagram embedding (S).** `--with-diagrams`: call the existing
`internal/diagram` mermaid path per context, embed the block, and add the
"explain this diagram" prompt step. Pass `--diagram-style` through to `ParseStyle`.

**Phase 4 — Synthesis + onboarding (M).** `--style onboarding`: the Opus
executive summary in `README.md` and the cross-context walkthrough, reasoning over
the whole export and the deterministically-computed automation chain. Cost
accumulation and `--show-cost`.

**Phase 5 — Drift gate (S).** `--check`: regenerate to a temp dir and diff against
the committed docs (text diff on the deterministic reference parts; for the LLM
prose, diff against a recorded generation or compare the structural `referenced`
sets — see Open Questions). Document the CI recipe. `--single-file` collapse.

## Risks & Mitigations

- **Hallucinated flows.** The headline risk. Mitigated structurally: the model is
  given the export as ground truth, returns the entities it referenced as
  structured output, and every reference is checked against emod's name set and
  flow edges before the doc is written. A reference to a non-existent event is
  caught, fed back, and regenerated; unresolved ones are flagged inline and fail
  `--strict`. The model is never the authority on what exists — the export is.
- **Plausible-but-wrong narrative.** A section can name only real entities yet
  describe their relationship wrongly. The faithfulness gate proves names and
  flows exist, not that the *prose around them* is right. Mitigations: ground each
  slice's prose on its own `#` comment (the author's stated intent) and instruct
  the model to defer to it; compute cross-context edges deterministically rather
  than letting the model infer them; keep diagrams emod-generated so the picture is
  always a true second source. Human review of generated docs is still expected —
  this lowers the cost of keeping docs, it does not remove the author.
- **Docs drift.** The reason to derive docs from the model at all. `--check` in CI
  fails the build when committed docs no longer match a fresh generation, so the
  docs cannot silently lag the source the way a hand-written page does.
- **Contradicting the author's comments.** The `#` comments are intent, not
  decoration. The prompt treats `comments[].text` as authoritative and instructs
  the model to surface a discrepancy ("the comment says X, the structure shows Y")
  rather than paper over it — turning a stale comment into a visible signal instead
  of silently-wrong prose.
- **Cost on large models.** Per-section Haiku keeps the bulk cheap; only two
  whole-model passes hit Opus. Cost is surfaced every run; `--with-diagrams` adds
  no model cost (emod draws). Section calls fan out concurrently to bound latency.
- **Non-determinism breaking `--check`.** LLM prose is not byte-stable, so a naive
  text diff would always report drift. Mitigated by making the *deterministic*
  parts (reference catalogue, embedded diagrams, the `referenced` entity sets) the
  primary drift signal, and by comparing recorded generations for the prose — see
  Open Questions.
- **Documenting a broken model.** The generator validates first and refuses to
  document a model with errors, so it never writes confident prose about flows that
  do not parse.

## Open Questions

- **What exactly does `--check` diff?** Byte-diffing LLM prose is hopeless. Options:
  (a) diff only the deterministic reference catalogue + embedded diagrams + the
  structural `referenced` sets, treating prose as advisory; (b) record the model
  responses (golden files) and diff against those; (c) hash the *export* and store
  it in the docs front-matter, regenerating prose only when the export hash
  changes. Leaning (c) — drift is fundamentally "did the model change?", which the
  export hash answers exactly and cheaply.
- **Reference style: LLM or pure render?** Phase 1 makes `reference` a pure,
  LLM-free render of the export. Is the prose-free catalogue good enough to keep as
  a zero-cost default, with LLM only for `narrative`/`onboarding`? Current lean:
  yes — a faithful catalogue with no model cost is a genuinely useful artefact.
- **Per-slice vs per-context prompt granularity.** Per-slice maximises Haiku
  cheapness and concurrency but can read as disjointed; per-context gives better
  flow at higher token cost. Possibly per-slice for `reference`/`narrative`,
  per-context for `onboarding`.
- **Diagram-per-context vs one big diagram.** Per-context mermaid blocks are
  readable; the full-model diagram is the better onboarding map but can be large.
  Likely: per-context on context pages, full model (projected style for DCB) on the
  onboarding page.
- **Surfacing lint findings in docs.** Should generated docs note where the model
  trips `internal/linter` rules (e.g. a `god-view`), as a "known modeling smells"
  appendix, or stay purely descriptive? Tempting as a nudge, but it blurs docs and
  review (proposal 03). Lean descriptive, with lint left to `emod lint`.
- **Field-level prose.** Reference style lists every field; should narrative prose
  describe field semantics, or only name the salient ones? Naming everything is
  noisy; choosing "salient" fields is a judgement the model may get wrong. Lean:
  list fields in reference, mention only flow-relevant fields in narrative.
